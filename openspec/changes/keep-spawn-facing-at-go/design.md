# Design

## Context

The race has one place where a racer is positioned at a map's start, and it is reached more than once.

- `CupSession.enterMap` (`voyager/platform/src/main/java/net/elytrarace/voyager/platform/cup/CupSession.java:698`) calls
  `Racers.faceCourse(player, map)` at `:700` during the countdown ticks. `Racers.faceCourse`
  (`.../platform/flight/Racers.java:104-106`) sets the racer's facing with `player.lookAt` on the centre of
  `map.rings().getFirst()`. Its only caller is that line.
- `CupSession.mapStarted` (`.../cup/CupSession.java:639`) runs at the GO tick and calls
  `transition.advanceTo(map, racers)` at `:650`. The racer is already in the instance, so the transition runs the
  same-instance branch of `Arrivals.reposition` (`.../platform/world/Arrivals.java:49`).
- `Arrivals.reposition` (`Arrivals.java:73-75`) calls `player.teleport(target, null, RelativeFlags.NONE, true)`. The
  target is the spawn `Pos` built in `MapTransition.java:111` by `Vectors.toMinestom(map.spawn()).asPos()`. That
  `Pos` has no explicit yaw or pitch, so both are 0 (the comment at `:110` says "a racer arrives looking north"). The
  teleport overwrites the facing that `faceCourse` set.
- The same spawn `Pos` reaches a racer through `Arrivals.java:61` (`setInstance`), `JoinArrival.java:41-43` (join spawn)
  and `LobbyTransition.java:34`. None of them faces the first ring.
- A reset is already right. `RunResetter.java:80,83` repositions the racer and then `Racers.place`
  (`Racers.java:125`) turns it with `lookAt`. This change does not touch that path.

The defect is therefore a second placement that carries no facing. The fix must make every placement at a map start
carry the facing of ring 0.

## Options

1. **Re-apply `faceCourse` after the GO teleport.** Small. It keeps two placements and one of them is still wrong for a
   moment, so a racer can see the spawn direction for a tick. Rejected.
2. **Drop the GO call to `advanceTo`.** The racer is already in the map, so the teleport is not needed. This changes
   the tick order that `cup-session-characterization` pins, which the golden masters forbid. Rejected.
3. **Give the spawn position its facing in one place, and use it for every arrival (chosen).** A single function
   computes the yaw and pitch from the spawn to the centre of ring 0 and returns the `Pos` with those values. `MapTransition`,
   `Arrivals` and `JoinArrival` use it. The GO call still teleports to the same position, now with the right facing, so
   the tick order does not change.

## Decision

Option 3. The facing is computed by one pure function in `voyager/platform` (a `flight` package helper next to
`Racers`), from the map's spawn and ring 0 only. It has no Minestom instance state, so a unit test can check it with plain
numbers. `Racers.faceCourse` and the new function must agree; `faceCourse` is then only used for an in-place turn during
the countdown and stays as it is.

Expected value for `elytraraceblueandred`: spawn (109, -62, 54), ring 0 centre (85, -54, 54). The horizontal offset is
(-24, 0), so yaw is 90 (facing west, -x). The pitch comes from the vertical offset against the horizontal distance; the
test asserts the pitch that the same geometry gives, not a fixed constant.

## Golden masters

The cup-session golden transcripts record each racer's client `Pos` with yaw and pitch (for example
`voyager/server/src/test/resources/golden/cup-session/lobby-and-start.txt`). The GO lines of the transcripts that
include a racer at the start change their yaw and pitch and nothing else. The fix commit updates those lines, reviewed
line by line. The move rule in `cup-session-characterization` ("never regenerated by the move") is not weakened: it is
a separate, explicit behaviour change, recorded in its own commit and listed in the PR.

The `race/waiting-lobby` requirement "Once a cup has started..." is modified in this change (`specs/race/waiting-lobby`)
so that its byte-for-byte scenario allows exactly that exception.
`cygnus-style-lobby` modifies the same requirement for the lobby action bar. Its delta names both exceptions, so the text
merged at archive keeps both.

## Computer racers

`race/com-racers` places computer bodies through `ComField.java:136`, which is not a player and not on the
`Arrivals` path. This change does not alter it. The test suite asserts the human racer only. Whether the COM
grid faces ring 0 is a question for the code PR's review; the task list checks it and records the answer.

## Architecture

| Type | Module | Package | Dependency direction |
|---|---|---|---|
| `Facing` (pure function, yaw and pitch from two points) | `voyager-platform` | `platform.flight` | uses `voyager-api` `Vec3` and `MapDefinition` only |
| changes to `MapTransition`, `Arrivals`, `JoinArrival` | `voyager-platform`, `voyager-server` | existing | platform uses Minestom; the server composition root wires `JoinArrival` |

No new type in `voyager-api` or `voyager-race`. The helper imports no DI annotation and no Minestom type. No
`voyager-fitness` rule is added or changed; the task list runs `./gradlew :voyager:fitness:test` to show the existing
rules still hold.

## Out of scope

- Reset placement (`RunResetter`, `Racers.place`), which stays as it is.
- Changing when the GO teleport happens.
- Sound, title or lobby display changes.

## Risks

- The expected yaw is derived from the shipped map. A map whose ring 0 sits directly above or below the spawn has no
  horizontal direction; the helper must define that case, and the test covers it.
- If `Vectors.toMinestom(...).asPos()` is used somewhere that the new function does not replace, a racer can still
  spawn facing 0. The task list includes a grep for `asPos()` on spawn values.
