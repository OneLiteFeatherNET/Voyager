# E3 Race Core Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `voyager-race` as pure domain — ring geometry, progression, scoring and the race state machine — so that a complete race, and a complete cup, can be played through in a JUnit run with no server.

**Architecture:** Ring geometry and configuration records live in `voyager-api`; `voyager-race` holds the collision test, the per-player progression tracker, the scoring services and the state machine. ECS handles only what happens every tick (progression, tick counters); everything at an event boundary — map completion, cup advancement, scoring — is a plain service. No Minestom, no Xerus, no persistence.

**Tech Stack:** Java 25, JUnit 6, AssertJ, ArchUnit (via `voyager-fitness`). No new runtime dependencies: the collision test is ten lines of vector arithmetic and does not justify commons-geometry.

**Spec:** `docs/superpowers/specs/2026-09-09-voyager-greenfield-design.md`, section "Race core (`voyager-race`)".

**Behaviour inventory:** the old tree's actual behaviour, with file:line for every claim, was collected before this plan was written. Where a task says "matches today", it was read out of the running code, not assumed.

## Global Constraints

- Java 25 for every `voyager-*` module. No Kotlin.
- Packages under `net.elytrarace.voyager.race..` and `net.elytrarace.voyager.api..`. The tree being replaced owns `net.elytrarace.api`, `net.elytrarace.server` and `net.elytrarace.setup` — never add to those.
- `voyager-api` contains interfaces, records, enums and exceptions only. No implementation, no I/O.
- Module dependencies point strictly left. The spec permits `voyager-race -> voyager-api, voyager-physics`, but **nothing in these nine tasks needs anything from `voyager-physics`**, so the dependency is not declared: ring geometry, progression, scoring, effects and the state machine all sit on `voyager-api` alone. Declare it in the task that first needs it, not before. `voyager-race` must not import Minestom, Xerus, Bukkit, Gson, Hibernate or anything from the tree being replaced.
- Build exception messages and similar output with `"...%s...".formatted(x)`, never `+` concatenation.
- Domain exceptions live in an `exception` subpackage next to the domain they belong to, each with its own `package-info.java`.
- Every package with sources declares `@NotNullByDefault` in `package-info.java`.
- Components are `record`s without exception; they are replaced, not mutated.
- Domain interfaces needing a controlled extension point are `sealed … permits BaseX` with a `non-sealed abstract BaseX`. Registries are `sealed` with a static `create()` and one `Default*` over `ConcurrentHashMap`, returning `@Unmodifiable` collections. Factories are `abstract` with a private constructor, `@ApiStatus.Internal`, and `@Contract` on every factory method.
- Enums with an external representation cache `VALUES` and expose `byName()` returning `Optional`.
- Commits follow Conventional Commits. No Co-Author trailer, no session trailer — a repository hook rejects them.

**Sequencing:** none. `voyager-api` and `voyager-physics` are both on `main` as of 1.10.0, and this stage needs only the former. Branch off `main`.

**Registering the module is part of Task 1, not an afterthought.** `voyager-fitness`'s `FitnessCoverageTest` holds every `voyager-*` module with production sources to two conditions: ArchUnit must import at least one of its classes, and at least one declared `@ArchTest` rule must name its package prefix. Adding `voyager-race` to `settings.gradle.kts` without adding it to `PACKAGE_PREFIX_BY_PROJECT` **and** giving it a rule fails that test. This is deliberate and must not be worked around by loosening the test.

## Decisions this plan implements

Seven were settled by reading the code; three were put to the product owner and answered.

| # | Decision | Source |
|---|---|---|
| D-E3-1 | A cup runs **every** map in its rotation. Today it loads map 2 and never runs it, because `LinearPhaseSeries` has no way back into the game phase — that is a defect, not behaviour to preserve; no player has ever seen map 2 run. | ruling |
| D-E3-2 | The ring hit area stays the **circumcircle** of the corner points, exactly as today. Tightening to the drawn polygon would make every ring measurably harder without announcement. | product owner |
| D-E3-3 | Ring order stays **strict**, and `RingType.BONUS` is **dropped**. It meant "optional off-route" while nothing is skippable, and it appears in no shipped map — all 32 portals are `STANDARD`. | product owner |
| D-E3-4 | Each map carries a **reference time**; medals are classified against it. Today the first finisher on a fresh map always gets `DIAMOND` and 60 bonus points, which distorts every cup containing a new map. | product owner |
| D-E3-5 | The ring **normal is stored**, not derived from two edge vectors. Today `computeNormal` takes the cross product of the first two edge vectors; in all 32 shipped portals those are opposite points, so the cross product is zero and the normal falls back to `(0,0,1)` — correct only because all 32 happen to lie in z-constant planes. The production map (35 portals, 18 x-constant, 9 y-constant, 8 z-constant) does exercise it. Storing it removes a computation that has never been tested by the shipped data. | ruling |
| D-E3-6 | Coordinates are `double` throughout. `LocationDTO` is `int` today while `GuidePointDTO` is `double`; the physics core needs `double`. | ruling |
| D-E3-7 | No elimination. Neither tree has a "player is out" state, and nothing asks for one. | ruling (YAGNI) |
| D-E3-8 | A practice mode exists in the domain as a **restart loop**, because the spec places "how a practice retry loops back" in `voyager-race`. It is minimal: no position bonus, no ranking, restart the same map. | ruling (spec) |
| D-E3-9 | The six behaviour statements of the old `RingCollisionSystemTest` are adopted as specified behaviour; the two stale classes (`startGameRegistersSystems`, `GameEntityFactoryTest`) are not. None of those 27 tests ever ran — they were committed already disabled — so they are a description to verify, never a result to trust. | ruling |
| D-E3-10 | Cup scoring is built, and it is new work. `CupScoring` exists in the old tree as dead code that nothing calls, and because of D-E3-1 it could never have run. The point values (ring 10, medal 60/45/30/15/5/0, position 10/6/3/1) have therefore **never been observed interacting across maps**. | ruling |

The geometry is `server`'s, because that is the behaviour players have: a **disc**, hit area the circumcircle of the corner points (D-E3-2), edge **inclusive**, tested over the segment between the previous and current tick position, direction **not** checked so a backwards pass counts.

package net.elytrarace.voyager.race.collision;

import net.elytrarace.voyager.api.math.Vec3;
import net.elytrarace.voyager.api.race.Ring;
import net.elytrarace.voyager.api.race.RingType;
import org.junit.jupiter.api.Test;

import static org.assertj.core.api.Assertions.assertThat;

class RingPassTest {

    /** Axis-aligned, facing +z, centred on the origin's column. */
    private static final Ring FLAT =
            new Ring(0, new Vec3(0.0, 64.0, 100.0), new Vec3(0.0, 0.0, 1.0), 5.0, 10, RingType.STANDARD);

    /**
     * Tilted in the xy plane and standing in negative z. Every fixture above it faces +z, where two
     * of the three components of every dot product vanish; this one keeps all three alive, which is
     * the only way a mistake in the x or y term can show up at all.
     */
    private static final Vec3 TILTED_NORMAL = new Vec3(0.6, 0.8, 0.0);
    private static final Ring TILTED =
            new Ring(3, new Vec3(10.0, 70.0, -20.0), TILTED_NORMAL, 4.0, 25, RingType.CHECKPOINT);

    @Test
    void countsAPassStraightThroughTheCentre() {
        assertThat(RingPass.crosses(new Vec3(0.0, 64.0, 99.0), new Vec3(0.0, 64.0, 101.0), FLAT)).isTrue();
    }

    @Test
    void countsAPassExactlyOnTheRim() {
        // The rim is inclusive, matching the old tree. distance == radius counts.
        assertThat(RingPass.crosses(new Vec3(5.0, 64.0, 99.0), new Vec3(5.0, 64.0, 101.0), FLAT)).isTrue();
    }

    @Test
    void rejectsAPassJustOutsideTheRim() {
        assertThat(RingPass.crosses(new Vec3(5.001, 64.0, 99.0), new Vec3(5.001, 64.0, 101.0), FLAT)).isFalse();
    }

    @Test
    void rejectsMovementParallelToTheRingPlane() {
        assertThat(RingPass.crosses(new Vec3(0.0, 64.0, 99.0), new Vec3(10.0, 64.0, 99.0), FLAT)).isFalse();
    }

    @Test
    void rejectsAPlaneTheSegmentStopsShortOf() {
        // The plane is at z=100; the segment ends at z=95, so the crossing would need t = 2.
        assertThat(RingPass.crosses(new Vec3(0.0, 64.0, 90.0), new Vec3(0.0, 64.0, 95.0), FLAT)).isFalse();
    }

    @Test
    void rejectsAPlaneAlreadyBehindTheSegment() {
        // Starting past the plane and moving away needs t = -0.25.
        assertThat(RingPass.crosses(new Vec3(0.0, 64.0, 101.0), new Vec3(0.0, 64.0, 105.0), FLAT)).isFalse();
    }

    @Test
    void countsABackwardsPass() {
        // Direction is deliberately not checked, matching the old tree: flying back through a ring
        // counts as passing it. Whether that should change is a gameplay decision, not this test's.
        assertThat(RingPass.crosses(new Vec3(0.0, 64.0, 101.0), new Vec3(0.0, 64.0, 99.0), FLAT)).isTrue();
    }

    @Test
    void countsAPassThroughATiltedRingsCentre() {
        // from = centre - normal, to = centre + normal, so the crossing sits exactly at t = 0.5 and
        // the intersection is the centre itself. All three coordinates differ between from and to.
        Vec3 from = new Vec3(9.4, 69.2, -20.0);
        Vec3 to = new Vec3(10.6, 70.8, -20.0);

        assertThat(RingPass.crosses(from, to, TILTED)).isTrue();
    }

    @Test
    void countsAnOffCentreHitOnATiltedRing() {
        // Aimed three blocks along +z from the centre, which lies in the tilted ring's own plane
        // because the normal has no z component. 3 < radius 4, so it counts.
        assertThat(RingPass.crosses(new Vec3(9.4, 69.2, -17.0), new Vec3(10.6, 70.8, -17.0), TILTED)).isTrue();
    }

    @Test
    void rejectsAnOffCentreMissOnATiltedRing() {
        // Same geometry, aimed five blocks out. 5 > radius 4.
        assertThat(RingPass.crosses(new Vec3(9.4, 69.2, -15.0), new Vec3(10.6, 70.8, -15.0), TILTED)).isFalse();
    }

    @Test
    void rejectsAZeroLengthStep() {
        // A stationary player produces from == to every tick. Without a guard the denominator is

        Vec3 standingStill = new Vec3(0.0, 64.0, 100.0);

        assertThat(RingPass.crosses(standingStill, standingStill, FLAT)).isFalse();
    }
}

- [ ] **Step 3: Write the implementation**

`RingType` is an enum of `STANDARD, BOOST, SLOW, CHECKPOINT`, caching `VALUES` as an unmodifiable list and exposing `static Optional<RingType> byName(String)` that trims, upper-cases with `Locale.ROOT`, and returns `Optional.empty()` for null, blank or unknown input. It must not throw on unknown input — map JSON is written by hand.

`Ring` is a record `(int index, Vec3 center, Vec3 normal, double radius, int points, RingType type)` whose compact constructor throws `InvalidRingException` when `index < 0`, when `radius <= 0`, when `points < 0`, or when the normal is not unit length. Use a tolerance of `1e-9` on `normal.length()`; an exactly-computed unit vector does not always square back to exactly 1.0.

`InvalidRingException extends RuntimeException`, in the `exception` subpackage, with its own `package-info.java`. Messages use `"...%s...".formatted(...)`.

`RingPass` is an `abstract` utility with a private constructor and `@ApiStatus.Internal`, holding one method:

```java
public static boolean crosses(Vec3 from, Vec3 to, Ring ring) {
    Vec3 step = to.minus(from);
    double denominator = ring.normal().dot(step);
    if (Math.abs(denominator) < PARALLEL_EPSILON) {
        return false;
    }
    double t = ring.normal().dot(ring.center().minus(from)) / denominator;
    if (t < 0.0 || t > 1.0) {
        return false;
    }
    Vec3 intersection = from.plus(step.scale(t));
    return intersection.distanceTo(ring.center()) <= ring.radius();
}
```

`PARALLEL_EPSILON` is `1e-8`, matching the old tree. The radius comparison stays exact — the rim is inclusive and no tolerance is added to it; a tolerance there would quietly enlarge every ring.

**`Vec3` today has `plus`, `minus`, `scale`, `length` and `lengthSquared` — it has neither `dot` nor `distanceTo`.** Add both to `Vec3` in `voyager-api`, each with its own tests, rather than open-coding the arithmetic in `RingPass`; they are general vector operations and belong on the type. Use `lengthSquared` inside `distanceTo` only if you also keep `distanceTo` returning the real distance — the radius comparison is against a distance, not its square, and switching one without the other is a silent change to every ring's size.

Give `dot` a test with three non-zero, mutually distinct components on both sides and a hand-computed expected value: with every component equal, or any of them zero, a `dot` that sums the wrong pair of products still returns the right number.

1. `t < 0.0 || t > 1.0` → `t < 0.0` (the segment becomes a ray).
2. `<= ring.radius()` → `< ring.radius()` (the rim becomes exclusive).
3. `Math.abs(denominator) < PARALLEL_EPSILON` → `denominator < PARALLEL_EPSILON`.
4. `ring.normal().dot(ring.center().minus(from))` → `ring.normal().dot(from.minus(ring.center()))` (sign flip).
5. In the intersection, `from.plus(step.scale(t))` → `from.plus(step)` (use the end point instead of the crossing).
6. In `Ring`'s constructor, drop the unit-length check.

## Task 7: The race state machine

**Files:**
- Create: `voyager-race/src/main/java/net/elytrarace/voyager/race/flow/RacePhase.java`

- Create: `voyager-race/src/main/java/net/elytrarace/voyager/race/flow/package-info.java`
- Create: `voyager-race/src/main/java/net/elytrarace/voyager/race/flow/exception/IllegalPhaseTransitionException.java`
- Test: `voyager-race/src/test/java/net/elytrarace/voyager/race/flow/RaceStateMachineTest.java`

**Interfaces:**
- Produces: `RacePhase { LOBBY, GAME, END }`; `RaceTimings(Duration lobby, Duration race, Duration end)` with a `DEFAULT`; `RaceState(RacePhase phase, int mapIndex, Duration inPhase, boolean cupFinished)`; `RaceStateMachine.advance(RaceState state, CupDefinition cup, RaceTimings timings, Duration step, boolean allPlayersFinished)` returning the next `RaceState`. Task 9 drives it in a loop; `voyager-platform` will drive it from Xerus later.

Xerus is Minestom-bound and must not appear here (spec). This module owns **which transitions exist**; the platform owns ticking, timers and delays. That split is what makes a whole race playable in a JUnit run — the end-to-end test the old tree never had, precisely because it was impossible without it.

Behaviour, with the two fixes from the decision table:

| From | Condition | To |
|---|---|---|
| `LOBBY` | `inPhase >= timings.lobby()` | `GAME`, `inPhase` reset |
| `GAME` | `inPhase >= timings.race()` **or** `allPlayersFinished` | `END`, `inPhase` reset |
| `END` | `inPhase >= timings.end()` and more maps remain and mode is `RACE` | `LOBBY`, `mapIndex + 1` (**D-E3-1**) |
| `END` | `inPhase >= timings.end()` and mode is `PRACTICE` | `LOBBY`, same `mapIndex` (**D-E3-8**) |
| `END` | `inPhase >= timings.end()` and it was the last map in `RACE` | stays `END`, `cupFinished` true |

Defaults match today: lobby 120 s, race 300 s (the old `DEFAULT_RACE_DURATION_TICKS` of 6000 at 20 TPS), end 100 s.

A state with `cupFinished` true is terminal: advancing it returns itself unchanged. Nothing throws for that — it is the normal end. `IllegalPhaseTransitionException` is for a `RaceState` whose `mapIndex` is out of range for the cup it is advanced against, which is a programming error rather than a game outcome.

- [ ] **Step 1: Write the failing test**

`RaceStateMachineTest` must cover at least:

- Lobby holds until its duration elapses, then moves to `GAME` with `inPhase` reset to zero — check the tick **before** the boundary too, not only the one at it.
- A race ends on the time limit.
- A race ends early when every player is finished, and `inPhase` is then well short of `timings.race()`.
- After `END`, a `RACE` cup with a second map returns to `LOBBY` with `mapIndex` 1. **This is the transition the old tree cannot make** — assert it explicitly and say so in the test.
- After the last map, `cupFinished` becomes true and further advancing changes nothing.
- `PRACTICE` returns to `LOBBY` on the same `mapIndex`, however many maps the cup has.
- A `mapIndex` beyond the cup's map list throws `IllegalPhaseTransitionException`.

Build the cup from **three** maps with distinct names, and use timings that are **not** all equal — for example lobby 5 s, race 20 s, end 3 s. Equal durations would let a machine that reads the wrong timing field pass every test.

Run `./gradlew :voyager-race:test` at each stage.

## Self-review notes for whoever executes this

Three things in this plan came from defects found the hard way earlier in this rebuild. They are worth knowing before you start.

**Fixture values are computed, never copied.** A brief in the previous stage carried a position at `y = 1.5` with a scan radius of `0.0` against a floor at `y == 0` — three values that cannot all be true at once. It shipped twice, in two different tasks, because the second was copied from the first. Every coordinate in this plan was derived; check them anyway, and if one does not add up, say so rather than making the test match the implementation.

**The constant-field sweep is a step in every task for a reason.** In the previous stage it found a real gap in every single task it was applied to, including twice in work I had already swept myself. The shape is always the same: a field left at one value across all fixtures, where the computation under test stops discriminating. Here the obvious candidate is the ring normal — `(0, 0, 1)` makes two of three dot-product terms vanish, which is exactly why the old tree's normal computation has never been exercised by its own shipped maps.

**A mutation that survives is a finding about the tests, not a licence to change the implementation.** If one of the listed mutations stays green, the test is the gap. Close it, and say in the report which test you added and which mutation it kills.
